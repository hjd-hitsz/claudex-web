# Claudex Web 前端设计

## 核心精神：主动对使用体验负责

前端设计的责任是让一个不了解实现的第三方，愿意接近这个产品，看得懂，用得顺，感到界面经过认真安排。设计者要主动承担这个判断，不能等编译器、测试或用户逐个指出问题。

后端实现常有较明确的契约：输入、输出、状态与失败条件，可以通过程序查证。前端同样需要技术正确，但它的主要成果还包括人如何感知、理解和使用界面。一个页面可以没有报错、元素没有溢出、每个按钮都能点击，同时显得笨重、零散、难找、费解。技术运行正确只完成了其中一部分工作。

**原则用于帮助看见问题，设计者负责判断整体是否好用、是否协调。没有违反某条原则，绝不构成接受一个设计的理由。** 面对一处生硬的布局，即使暂时说不出它违反了哪条规范，也应认真对待这种不协调，尝试调整、比较、继续理解。缺少明确的错误信号时，更需要主动观察和取舍。

本技能培养这种工作方式。项目的功能约定、可访问性要求、架构边界和技术检查继续遵循 `AGENTS.md` 与相关文档；它们提供必要条件，整体设计仍由实际体验来判断。

## 先成为那个第三方使用者

打开真实页面，带着一个实际目的去用。暂时放下对代码、接口、控件位置的熟悉，设想自己刚安装这个项目，只知道想完成什么。让页面自己带路，从进入产品、发现入口、判断状态、执行操作，一直用到离开，再过一会儿回来。

例如，想知道软件有没有新版本，就从平时的主界面开始。若必须记得设置里藏着版本检查，才能发现已经有更新，发现这件事的负担就被交给了用户。想配置一个后端，就从识别后端、理解是否可用、找到配置和保存开始；对着实现说明才能明白的步骤，值得重新组织。

实际点击、阅读、等待、关闭，再回来。留意自己什么时候需要停下来辨认，什么时候目光在页面上来回搜索，什么时候不知道操作是否完成，什么时候已经做完了事情却还被提示纠缠。这些感受就是设计工作的材料。通过脚本直接定位按钮可以测试按钮的行为，用户寻找按钮的过程则需要亲自体验。

设计者熟悉自己刚做的界面，很容易把记忆误当成清晰。可以从不同入口重走流程，隔一段时间再看，或与成熟产品里相似的任务并排比较。这样的代入用于发现问题；面对真实用户的新反馈，继续修正自己的理解。

## 从整页的表达开始理解审美

先感受页面在传达什么。Claudex Web 是日常对话与工作工具，本项目追求的是清楚、紧凑、安静、利落：工作内容受到重视，操作容易理解，辅助信息各得其所。这样的气质需要内容、排布、字体、颜色和交互共同形成。

看整页时，体会目光最先落在哪里，接下来往哪里走，哪些内容自然形成一组，哪些地方突然中断了阅读。一个很醒目的按钮会改变整页的重心；几段看似不起眼的说明叠在一起，也会把简洁的设置变成一页负担。局部是否精致，要放回整体判断。

再进入细节：图标与文字的分量是否相称，版本号是否抢了名称的注意力，按钮是否像同一个产品里的按钮，卡片是否有舒展且连贯的节奏。数学居中和视觉居中可能有差异，同样的尺寸也可能因为字形、内容或相邻元素而呈现不同重量。尺寸体系帮助保持秩序，眼睛仍需要参与调整。

空白同样在表达关系。它可以让信息呼吸，也可以把本应连在一起的内容扯散。边框可以帮助归属，也可以把一个自然的整体切得支离破碎。这里的选择取决于页面想表达的关系，不能靠“用了统一间距”或“采用了标准组件”结束判断。

## 领会紧凑的目的

本项目反复强调减少无用的空间占用，背后是尊重用户的注意力和工作空间。一个版本号独占一行，消耗的既有高度，也有用户重新扫视和建立联系的精力。相关信息放到一起，往往能让页面同时更短、更清楚。

但把所有间距都缩小，也可能制造新的拥挤。要先理解内容之间的关系，再决定删除、合并、弱化、展开或留白。当前版本与新版本一起阅读最自然；后端名称与其版本可以作为一个身份整体；一组相关操作适合集中安排。独立的任务仍需要呼吸和边界。

两行偏好之间的大空洞，会让它们显得彼此疏远；紧贴卡片边缘又会让内容局促。值得调整的是这种整体感受。用尺量出距离有助于定位原因，最终要回到真实字号、卡片大小、上下文和页面密度里感受它是否自然。

用户指出“这里太空”时，应重新审视整个区域的组织。单独减去几像素，可能保留了信息被拆散、操作游离、说明冗余等更深的问题。

## 用这次项目中的取舍理解设计

更新区域曾把版本、状态和操作拆开：名称附近放当前版本，别处再放最新版本，左下角留一句状态，右下角摆操作。它们各自都有内容，组合起来却要求用户自己拼出含义。把相关版本放在一起，让更新按钮直接表达目标版本，把操作组成稳定的一排，能形成一段更连贯的阅读与行动。

这也解释了为何“无需更新”放进原来的按钮位置更合适：用户能沿着熟悉的位置理解当前状态，页面保持安定。这个例子的经验是理解状态与动作的关系；其他任务仍须结合自己的内容安排。

删除设置卡片里的多余分割线，改变的不只是线条数量。页面原先依赖一道道边界切割内容，调整后要靠更清楚的归属和更合适的距离重新形成整体。省下来的视觉负担应当由好的组织来承接。

“最新版本”前加发布渠道，暴露的是实现者的关注点。用户此刻关心能获得什么、是否值得操作。文字、图标、徽标与控件都应从这个视角选择，必要的解释出现在用户真正需要理解它的位置。

这些取舍都源于同一件事：站在使用者的位置，把散落的实现信息整理成自然的体验。学习例子时理解它为什么更合适，再将这个判断迁移到新场景。

## 交互也有节奏与分寸

用户点击后需要知道发生了什么，也需要在事情结束后把注意力收回来。一次操作的反馈若不断驻留、重现，就会让人反复怀疑服务还没恢复，或者自己漏做了什么。提示的结束方式属于这段体验本身。

实际使用时体会操作前后的连续性：点击是否得到及时回应，等待是否让人安心，受阻时是否知道如何继续，返回页面时是否像正常回来一样自然。成功反馈、当前故障和历史记录承担不同作用，应放在各自合适的位置和时间。

本项目重启完成后提醒用户刷新，关闭设置或刷新页面就结束这次提醒；忙碌时简短说明，结束本次请求，用户稍后再试。这些具体行为由产品契约维护。设计时还要感受它们出现得是否合时、措辞是否恰当，以及是否打断了用户真正想做的事。

## 靠观察、比较和推敲形成判断

遇到拿不准的地方，先找一个完成相似任务的成熟界面，观察它如何安排内容、建立重点、处理空白与操作。学习它作取舍的理由，再回到本项目的内容和使用环境。单独复制一个按钮或一组间距，往往得不到参考界面的整体品质。

在问题所在区域尝试有意义的变化。比如，一版保留独立说明，一版把状态融入操作；或者改变信息的分组方式，观察整个区域是否更易理解。差异应足以帮助理解问题，在比较中形成有理由的选择。对于已经明确的小调整，可以直接完成，无需额外制造方案。

每次调整后回到完整页面，看它是否和周围内容相处得更好，再亲自操作一遍。某个局部变漂亮却令主任务更难找，就需要继续取舍。觉得“不太对劲”时，把模糊感受说具体：哪一块过重、哪里阅读断开、什么需要额外猜测、哪个空白让内容失去联系，然后继续调整。

截图是一起观看设计的载体，技术测试帮助排除行为故障；设计质量依赖设计者对所呈现体验的持续判断。交付时说明自己作了什么取舍、改善了怎样的感受，展示真实浏览器里的关键画面。技术检查结果另行如实交代，审美判断由具体设计及实际使用承担。

## 阅读资料时带着设计问题

以下材料用于学习观察与取舍的方法。阅读后回到正在设计的界面，尝试解释和改善一处具体体验。

- [Apple：Principles of great design](https://developer.apple.com/videos/play/wwdc2026/250/) 将设计视为有意图的创造，说明原则需要结合情境作取舍；其 simplicity 与 craft 部分适合理解清晰、简洁和细致打磨的关系。
- [Apple：10 Questions with Design Evangelism](https://developer.apple.com/news/?id=s8sl4tpa) 讨论设计“不太对劲”时的批评与反思，以及如何围绕用户目标取舍内容。借此练习审视自己已熟悉的设计。
- [NN/g：Proximity Principle in Visual Design](https://www.nngroup.com/articles/gestalt-proximity/) 通过案例解释距离如何影响归属与发现。借此重新观察页面的阅读关系，而非套用一个固定间距。
- [Refactoring UI 官方公开页面](https://refactoringui.com/) 展示减少边框的设计示例，并公开层级、空间与文字等主题。这里引用其公开材料；进一步学习时关注前后画面的关系变化及适用情境。
